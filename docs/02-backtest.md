# การ Backtest และการจูน Threshold

## วิธีวัด

หลังสัญญาณติดในสัปดาห์ `t` วัดผลตอบแทนราคาที่ `t+1`, `t+4`, `t+8` สัปดาห์
แล้วเทียบกับผลตอบแทนเฉลี่ยของ **ทุกสัปดาห์** ในชุดข้อมูลเดียวกัน

```
edge  = mean(fwd_ret | มีสัญญาณ) − mean(fwd_ret | ทุกสัปดาห์)
t     = edge / (sd / √n)
hit   = สัดส่วนครั้งที่ราคาไปในทิศทางที่กฎทำนาย
```

การเทียบกับ baseline สำคัญมาก เพราะทองคำมีแนวโน้มขาขึ้นในระยะยาว
ถ้าวัดแค่ "S1 แล้วราคาขึ้นกี่ครั้ง" จะได้ตัวเลขสวยงามโดยที่กฎไม่ได้ทำอะไรเลย

**การป้องกัน look-ahead:** ทุกฟีเจอร์ (z-score, percentile 52 สัปดาห์, ret_4w)
คำนวณจากหน้าต่างที่ปิดที่สัปดาห์ปัจจุบัน ส่วนผลตอบแทนที่ใช้วัดเป็นอนาคตล้วน
ทั้งสองส่วนจึงแยกขาดจากกัน

ผลทั้งหมดบันทึกลง `backtest_results.csv`

## ผลจากการรันตรวจกลไก (ข้อมูลสังเคราะห์ 508 สัปดาห์)

| สัญญาณ | n | edge @4w | t | hit |
|---|---|---|---|---|
| S1 | 46 | −0.48% | −1.53 | 48% |
| S2 | 47 | −0.12% | −0.41 | 45% |
| S3 | 4 | −0.80% | −1.13 | 75% |

ไม่มีช่องไหนที่ \|t\| ≥ 2 — บนข้อมูลสุ่ม กฎไม่มี edge ซึ่งเป็นผลที่ควรได้
ถ้ากฎให้ผลสวยงามบนข้อมูลสุ่ม แสดงว่าโค้ดวัดผลผิด

**ตัวเลขข้างต้นใช้ตัดสินใจไม่ได้** ใช้ยืนยันได้เพียงว่า harness วัดค่าได้ถูก

## สิ่งที่พบระหว่างทดสอบ และควรแก้ก่อนใช้ข้อมูลจริง

**1. S3 ติดน้อยเกินกว่าจะสรุปทางสถิติ**
ที่ค่าเริ่มต้น S3 ติดเพียง 4 ครั้งใน 508 สัปดาห์ (0.8%) แม้ข้อมูลจริง 10 ปี
ก็น่าจะได้ n ราว 5–15 ครั้ง ซึ่งน้อยเกินกว่าจะแยก edge ออกจากความบังเอิญ
ทางแก้: ประเมิน S3 ด้วยเกณฑ์เชิงคุณภาพ (ติดตรงจุดกลับตัวจริงกี่ครั้ง) ควบคู่กับสถิติ
หรือผ่อนเงื่อนไขให้ต้องเข้าเพียง 2 ใน 3 ข้อ แล้วใช้ confidence แยกความเข้ม

**2. Grid search 75 ชุดบนข้อมูลชุดเดียวเสี่ยง overfit**
ชุดที่ได้คะแนนสูงสุดในตารางคือ `min_contracts=8000, price_high_pct=70`
ซึ่งบนข้อมูลสุ่มย่อมเป็นการเลือก noise ที่ดูดีที่สุด
ก่อนใช้ค่าจากตารางกับข้อมูลจริง ควร:
- แบ่งข้อมูลเป็น in-sample (เช่น 2015–2021) และ out-of-sample (2022–ปัจจุบัน)
  เลือกพารามิเตอร์จากช่วงแรก แล้ววัดผลบนช่วงหลังเพียงครั้งเดียว
- ดูว่าคะแนนเปลี่ยนแบบราบรื่นตามพารามิเตอร์หรือกระโดด — ถ้ากระโดด คือ noise
  ควรเลือกค่าที่อยู่กลางบริเวณที่คะแนนดีต่อเนื่อง ไม่ใช่ยอดแหลมเดี่ยว

**3. ค่าเริ่มต้น `min_contracts = 2,000` ที่ผมตั้งไว้แทบไม่ทำงาน**
คะแนนเฉลี่ยของ `min_contracts` ที่ 0, 1,000 และ 2,000 เท่ากันเป๊ะทุกทศนิยม
แปลว่าด่านนี้ไม่เคยตัดสัปดาห์ไหนออกเลย เพราะ Δ ของ Managed Money
แกว่งระดับหมื่นสัญญาต่อสัปดาห์เป็นปกติ เกณฑ์ 2,000 จึงต่ำเกินกว่าจะกรองอะไรได้
ความต่างเริ่มปรากฏที่ 8,000 เท่านั้น

ในข้อมูลจริง ส่วนเบี่ยงเบนมาตรฐานของ Δ MM net รายสัปดาห์อยู่ราวหมื่นถึงสองหมื่นสัญญา
ค่าเริ่มต้นในตาราง `signal_rule` จึงควรปรับขึ้นเป็นราว 8,000–12,000
หรือตัดด่านนี้ทิ้งแล้วพึ่ง z-score อย่างเดียวเพื่อลดพารามิเตอร์ที่ต้องจูน
ตัดสินหลังรันบนข้อมูลจริงแล้วดูว่าด่านไหนกรองได้จริง

**4. ความไวของพารามิเตอร์ทั้งกริดต่ำมาก**
คะแนนทั้ง 75 ชุดอยู่ในช่วง −0.32 ถึง +0.14 เท่านั้น และ `z_threshold`
สูงขึ้นให้คะแนนแย่ลงแบบเป็นเส้นตรง ซึ่งบนข้อมูลสุ่มคือสิ่งที่ควรเกิด
(กรองเข้มขึ้น → n น้อยลง → ประมาณค่าแย่ลง) ให้ใช้รูปแบบนี้เป็นเกณฑ์เทียบ:
ถ้ารันบนข้อมูลจริงแล้วยังได้ความไวราบเรียบแบบเดียวกัน แปลว่ากฎยังไม่จับอะไรได้

## เกณฑ์ตัดสินว่ากฎ "ใช้ได้"

ก่อนนำสัญญาณไปใช้จริง ควรผ่านทั้งสามข้อ:

1. edge ที่ +4w ถูกทาง และ \|t\| ≥ 2 บนช่วง out-of-sample
2. n ≥ 20 ครั้งสำหรับ S1 และ S2 (S3 ใช้เกณฑ์เชิงคุณภาพประกอบ)
3. ผลไม่พลิกขั้วเมื่อขยับ threshold ขึ้นลงหนึ่งขั้นในกริด

ถ้าไม่ผ่าน ทางเลือกที่ดีกว่าการฝืนจูนต่อคือลดสถานะของระบบจาก
"สัญญาณซื้อขาย" เป็น "เครื่องมืออธิบายบริบทตลาด" ซึ่งยังมีประโยชน์
