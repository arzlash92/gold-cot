# GoldCOT Signal — เอกสารออกแบบระบบ (System Design)

ระบบอ่านสัญญาณเคลื่อนไหวราคาทองคำจากข้อมูล COT ของ CFTC
Tech stack: **Python (Backend) · HTML5 + JavaScript + TailwindCSS (Frontend) · MySQL 8 (Database)**

---

## 1. เป้าหมายและขอบเขต

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | แปลงหลักการ "Level ไม่สำคัญเท่า Change" ให้เป็นกฎเชิงตัวเลขที่คำนวณซ้ำได้ แล้วส่งสัญญาณ 4 แบบพร้อมคะแนนความเชื่อมั่น |
| ความถี่ข้อมูล | รายสัปดาห์ — CFTC เก็บสถานะ ณ วันอังคาร ปิดตลาด และเผยแพร่วันศุกร์ 15:30 ET |
| สินค้าอ้างอิง | GOLD — COMEX contract code `088691`, ชุดข้อมูล **Disaggregated Futures-and-Options Combined** |
| ผู้ใช้ | เทรดเดอร์รายบุคคล / ทีมวิเคราะห์ ดูผ่าน Dashboard เดียว |
| ไม่อยู่ในขอบเขต | การส่งคำสั่งซื้อขายอัตโนมัติ, ข้อมูล intraday |

**หมายเหตุด้านความเสี่ยง:** COT เป็นข้อมูลล่าช้า 3 วันทำการ สัญญาณที่ระบบออกจึงเป็น *บริบทเชิงโครงสร้าง* ไม่ใช่จุดเข้าออกออเดอร์ ระบบต้องแสดงวันที่ของข้อมูล (as-of) ควบคู่กับวันที่เผยแพร่เสมอ เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่าเป็นข้อมูลสด

องค์ประกอบ:

- **ETL Pipeline** — ดึง COT, ราคา, Option OI ทำความสะอาด แล้วเขียนลงตาราง raw
- **Derivation Layer** — คำนวณ Net, Δ (สัปดาห์ต่อสัปดาห์), z-score, percentile 3 ปี เก็บลง `cot_derived`
- **Signal Engine** — อ่าน `cot_derived` + บริบทราคา แล้ว evaluate กฎ S1–S4 เขียนลง `signal`
- **API Layer** — FastAPI ให้ frontend เรียก
- **Scheduler** — APScheduler ยิงงานทุกวันเสาร์ 05:00 ICT (หลัง CFTC เผยแพร่)

## 3. โครงสร้างข้อมูล (MySQL)

ไฟล์เต็มอยู่ที่ `db/schema.sql` สรุปตารางหลัก:

| ตาราง | หน้าที่ | คีย์สำคัญ |
|---|---|---|
| `contract` | ทะเบียนสัญญาที่ติดตาม (เริ่มที่ทองคำ ต่อยอดไป Silver/Copper ได้) | `cftc_code` |
| `cot_raw` | ตัวเลขดิบจาก CFTC รายสัปดาห์ ไม่แก้ไขหลังบันทึก | `UNIQUE(contract_id, report_date)` |
| `cot_derived` | Net / Δ / z-score / percentile — ชั้นที่ Signal Engine ใช้จริง | `UNIQUE(contract_id, report_date)` |
| `price_daily` | ราคาทองรายวัน (OHLC) | `UNIQUE(symbol, trade_date)` |
| `price_weekly` | ราคาปิดวันอังคาร map ตรงกับ `report_date` เพื่อเทียบสถานะกับราคา ณ เวลาเดียวกัน | `UNIQUE(symbol, report_date)` |
| `option_oi` | Open Interest รายราคาใช้สิทธิ แยก call/put ต่อวันและต่อ expiry | `UNIQUE(contract_id, trade_date, expiry_date, strike, option_type)` |
| `signal` | ผลลัพธ์สัญญาณต่อสัปดาห์ พร้อม score, confidence, เหตุผลเป็น JSON | `UNIQUE(contract_id, report_date, signal_code)` |
| `signal_rule` | ค่า threshold ที่ปรับได้จากหน้าแอดมิน โดยไม่ต้อง deploy ใหม่ | `UNIQUE(signal_code, version)` |
| `job_run` | บันทึกการทำงานของ ETL ทุกครั้ง ใช้ตรวจสอบย้อนหลังเวลาข้อมูลหาย | `started_at` |

**เหตุผลการแยก `cot_raw` กับ `cot_derived`:** CFTC มีการแก้ไขข้อมูลย้อนหลังเป็นครั้งคราว การเก็บดิบไว้แยกทำให้คำนวณชั้น derived ใหม่ทั้งหมดได้โดยไม่ต้องดึงข้อมูลซ้ำ และตรวจสอบได้ว่าสัญญาณเปลี่ยนเพราะกฎเปลี่ยนหรือเพราะข้อมูลเปลี่ยน

## 4. หัวใจของระบบ: การแปลงเงื่อนไขให้เป็นตัวเลข

เอกสารต้นฉบับเขียนเงื่อนไขเป็นภาษาคน เช่น "Managed Money เพิ่มสถานะซื้อสุทธิอย่างต่อเนื่อง" ระบบต้องนิยามให้ชัดว่า *เพิ่มเท่าไรถึงนับ* ไม่งั้นความผันผวนปกติจะจุดสัญญาณทุกสัปดาห์

### 4.1 การกรองสัญญาณรบกวน (Significance Filter)

สำหรับทุกซีรีส์ `x` (mm_net, swap_net, mm_long, swap_short, prod_short):

```
d_x(t)  = x(t) − x(t−1)
z_x(t)  = d_x(t) / stdev(d_x, 52 สัปดาห์ล่าสุด)
```

การเปลี่ยนแปลงจะ "นับ" ก็ต่อเมื่อผ่านทั้งสองด่าน:

```
|z_x(t)| ≥ 0.75   และ   |d_x(t)| ≥ 2,000 สัญญา
```

ด่านแรกกันความผันผวนตามฤดูกาล ด่านที่สองกันกรณีตลาดนิ่งมากจน stdev เล็กผิดปกติแล้ว z พองเกินจริง

### 4.2 บริบทราคา (Price Context)

```
ret_4w      = close(t) / close(t−4) − 1
pct_52w     = อันดับเปอร์เซ็นไทล์ของ close(t) ในกรอบ 52 สัปดาห์

price_state = UP    ถ้า ret_4w > +1.5%
              DOWN  ถ้า ret_4w < −1.5%
              FLAT  นอกนั้น

price_zone  = HIGH  ถ้า pct_52w ≥ 80
              LOW   ถ้า pct_52w ≤ 20
              MID   นอกนั้น
```

`price_zone = HIGH` คือการนิยาม "ราคายังยืนในระดับสูง" ของสัญญาณที่ 3 ให้เป็นตัวเลข

### 4.3 กฎสัญญาณ

> ข้อควรระวังเรื่องเครื่องหมาย: "Δ Net Short ของ Swap Dealer เพิ่มขึ้น" มีค่าเท่ากับ **`d_swap_net < 0`** เพราะ `swap_net = long − short` ระบบเก็บทุกอย่างเป็น net long เสมอเพื่อกันความสับสน

| รหัส | ชื่อ | เงื่อนไข (ทุกข้อต้องเป็นจริง) | ทิศทาง |
|---|---|---|---|
| **S1** | Bullish Momentum | `price_state = UP` และ `d_mm_net > 0` (นัยสำคัญ) และ `d_swap_net < 0` (นัยสำคัญ) | 🟢 ขาขึ้น |
| **S2** | Momentum Weakening | `price_zone ∈ {HIGH, MID}` และ `price_state ∈ {UP, FLAT}` และ `d_mm_net < 0` (นัยสำคัญ) และไม่เข้าเงื่อนไข S3 | 🟡 เตือน |
| **S3** | Unwinding / Reversal | `price_zone = HIGH` และ `d_mm_long < 0` (นัยสำคัญ) และ `d_swap_short < 0` (นัยสำคัญ) | 🔴 กลับตัว |
| **S4** | Physical Hedge | `d_prod_short` มีนัยสำคัญ — เป็นชั้นบริบท ไม่ใช่สัญญาณเดี่ยว | 🔵 บริบท |

**ลำดับความสำคัญเมื่อชนกัน:** S3 > S1 > S2 เพราะ S3 คือการคลายสถานะทั้งสองฝั่งพร้อมกัน ซึ่งเป็นโครงสร้างที่เอกสารต้นฉบับระบุว่าน่าเชื่อถือสูงสุด ส่วน S4 แสดงคู่ขนานเสมอ

การตีความ S4 ตามบริบทราคา:

- ราคาขึ้น + Producer เพิ่ม Short → กำลังทยอยล็อกกำไรฝั่ง Physical แรงขายมีอยู่เหนือตลาด (ถ่วงลบเบา ๆ)
- ราคาลง + Producer ลด Short → ผู้ผลิตมองว่าราคาต่ำพอจะหยุดล็อก อาจเป็นสัญญาณพื้นราคา (ถ่วงบวกเบา ๆ)

### 4.4 คะแนนทิศทาง (Bias Score) และความเชื่อมั่น

รวมทุกมิติเป็นเลขเดียวช่วง −100 ถึง +100 เพื่อให้เห็นแนวโน้มต่อเนื่อง ไม่ใช่แค่ป้ายสัญญาณกระโดดไปมา:

```
raw = 0.50·z_mm_net  +  0.25·(−z_swap_net)  +  0.10·(−z_prod_short)  +  0.15·z_price_mom
ถ้าเข้าเงื่อนไข S3:  raw −= 1.20 · mean(|z_mm_long|, |z_swap_short|)
bias = clamp(round(raw × 35), −100, +100)
```

น้ำหนัก 0.50 ให้ Managed Money เพราะเป็นผู้กำหนดทิศทางราคาโดยตรง ส่วน Swap Dealer ได้ 0.25 ในฐานะฝ่ายรับความเสี่ยงอีกด้าน — ยืนยันโครงสร้างได้แต่ไม่ใช่ต้นเหตุ

**Confidence (0–100)** คำนวณจากสามส่วน: จำนวนองค์ประกอบที่ผ่านนัยสำคัญ (40), ขนาด |z| เฉลี่ย (30), จำนวนสัปดาห์ติดต่อกันที่ทิศทางเดียวกัน (30) สัญญาณที่มาสัปดาห์เดียวแล้วหายจึงได้คะแนนต่ำโดยอัตโนมัติ

## 5. Backend (Python)

### 5.1 ไลบรารีและโครงไฟล์

```
backend/
├── app/
│   ├── main.py            # FastAPI app + routes
│   ├── config.py          # อ่าน env
│   ├── db.py              # SQLAlchemy engine / session
│   ├── models.py          # ORM models
│   ├── etl.py             # ดึง CFTC + ราคา + option OI
│   ├── derive.py          # คำนวณ net / delta / z-score
│   ├── signal_engine.py   # กฎ S1–S4 + scoring   ← หัวใจ
│   └── scheduler.py       # APScheduler weekly job
├── tests/
└── requirements.txt
```

| ไลบรารี | ใช้ทำอะไร |
|---|---|
| `fastapi` + `uvicorn` | REST API |
| `SQLAlchemy 2.x` + `PyMySQL` | ORM และการเชื่อมต่อ MySQL |
| `pandas` + `numpy` | rolling stdev, percentile, การจัด timeline |
| `httpx` | ดึงข้อมูลจาก CFTC Socrata และ price feed |
| `APScheduler` | ตั้งเวลางานรายสัปดาห์ |
| `pydantic` | schema ของ request/response |

### 5.2 ปลายทาง API

| Method | Path | คืนอะไร |
|---|---|---|
| `GET` | `/api/v1/signals/latest` | สัญญาณล่าสุด + bias + confidence + เหตุผลรายข้อ |
| `GET` | `/api/v1/signals?from=&to=` | ประวัติสัญญาณ ใช้ทำตารางย้อนหลัง |
| `GET` | `/api/v1/timeline?weeks=104` | **ชุดข้อมูลรวม 5 มิติบนเส้นเวลาเดียว** — ราคา, Δ position, COT baseline, option OI, strike |
| `GET` | `/api/v1/cot/latest` | ภาพรวมสถานะทุกกลุ่มสัปดาห์ล่าสุด |
| `GET` | `/api/v1/options/strike-map?expiry=` | OI แยกตาม strike สำหรับหาแนวรับ/แนวต้านซ่อน |
| `GET` | `/api/v1/rules` / `PUT /api/v1/rules/{code}` | อ่าน/ปรับ threshold |
| `POST` | `/api/v1/admin/ingest` | สั่ง ETL ทันที (ป้องกันด้วย API key) |
| `GET` | `/api/v1/health` | สถานะระบบ + วันที่ข้อมูลล่าสุด |

`/timeline` เป็น endpoint ที่ตอบโจทย์ "The Unified Timeline Blueprint" โดยตรง — frontend เรียกครั้งเดียวได้ครบทั้ง 5 มิติที่ align ด้วย `report_date` เหมือนกัน ไม่ต้องต่อข้อมูลเองฝั่ง client

### 5.3 ลำดับงานรายสัปดาห์

```
เสาร์ 05:00 ICT
  1. ingest_cot()        ← CFTC Socrata, contract 088691
  2. ingest_price()      ← ราคารายวัน แล้ว snap ปิดวันอังคารเข้า price_weekly
  3. ingest_option_oi()  ← CME settlement file
  4. rebuild_derived()   ← คำนวณ 156 สัปดาห์ล่าสุดใหม่ทั้งช่วง (กันกรณี CFTC revise)
  5. evaluate_signals()  ← เขียน signal ของสัปดาห์ล่าสุด
  6. notify()            ← แจ้งเตือนเมื่อ S3 ติด หรือ bias พลิกขั้ว
```

ทุกขั้นเขียน `job_run` และเป็น idempotent — รันซ้ำวันเดิมได้ผลเท่าเดิม ใช้ `INSERT ... ON DUPLICATE KEY UPDATE`

## 6. Frontend

หน้าเดียว โฟกัสที่การเทียบ "ราคา ณ ระดับใด" กับ "ใครเพิ่มใครลด" บนแกนเวลาเดียวกัน

```
┌───────────────────────────────────────────────────────────────┐
│  GoldCOT Signal        ข้อมูล ณ 25 ส.ค. 2026 · เผยแพร่ 28 ส.ค.  │
├──────────────────┬────────────────────────────────────────────┤
│  สัญญาณสัปดาห์นี้   │  Bias −62   Confidence 78                  │
│  🔴 S3 คลายสถานะ  │  เหตุผล: MM ลด Long 18.4k · Swap ลด Short   │
│                  │  12.1k · ราคาอยู่เปอร์เซ็นไทล์ 91 ของ 52 สัปดาห์ │
├──────────────────┴────────────────────────────────────────────┤
│  ▌▌▌▌▌▌▌▌▌▌▌▌▌▌  แถบสถานะรายสัปดาห์ 52 ช่อง (signature)        │
│  แต่ละช่อง: บนคือ Δ Managed Money  ล่างคือ Δ Swap Dealer         │
├───────────────────────────────────────────────────────────────┤
│  กราฟเส้นเวลาเดียว: ราคา (เส้น) + Net position รายกลุ่ม (แท่ง)   │
├────────────────────────────┬──────────────────────────────────┤
│  แผนที่ Strike / Option OI  │  ตารางสัญญาณย้อนหลัง               │
└────────────────────────────┴──────────────────────────────────┘
```

**ทิศทางการออกแบบ**

- พื้นหลังกระดาษสีเทาเย็น `#EDF0F4` กับหมึก `#141C26` — อ่านตัวเลขหนาแน่นได้นานโดยตาไม่ล้า ต่างจากธีมเทอร์มินัลดำที่ใช้กันทั่วไป
- สีถูกใช้เป็น *ข้อมูล* ไม่ใช่การตกแต่ง: Managed Money `#0E7C7B`, Swap Dealer `#7A3E9D`, Producer `#B07407` สีเดียวกันนี้ใช้ทุกที่ทั้งกราฟ แถบ และตาราง ผู้ใช้จำได้ว่าสีไหนคือใครโดยไม่ต้องดู legend ซ้ำ
- ตัวอักษร IBM Plex Sans Thai สำหรับเนื้อหา และ IBM Plex Mono สำหรับตัวเลขทุกตัว เพื่อให้หลักตรงกันเวลาเทียบค่าในแนวตั้ง
- **Signature element** คือแถบสถานะ 52 ช่อง แต่ละสัปดาห์เป็นแท่งคู่กระจายจากเส้นกลาง อ่านจังหวะการสะสมและการคลายสถานะได้ในสายตาเดียว พื้นหลังช่องแต้มสีตามสัญญาณที่ติดสัปดาห์นั้น

ไฟล์ `frontend/index.html` รันได้ทันที มีข้อมูลตัวอย่างฝังไว้ และสลับไปดึงจาก API ได้ด้วยการตั้ง `API_BASE`

## 7. การทดสอบและตรวจสอบความถูกต้อง

1. **Unit test กฎสัญญาณ** — สร้างสัปดาห์สังเคราะห์ที่บังคับให้แต่ละกฎติด/ไม่ติด ตรวจว่าลำดับความสำคัญ S3 > S1 > S2 ทำงานถูก
2. **Backtest** — ยิงกฎย้อนหลัง 5 ปี วัดผลตอบแทนของราคาที่ +1/+4/+8 สัปดาห์หลังสัญญาณ เทียบกับค่าเฉลี่ยทุกสัปดาห์ ถ้าไม่ต่างจาก baseline อย่างมีนัย แปลว่ากฎยังไม่มีค่า
3. **ตรวจความถูกต้องของข้อมูล** — ยอด long รวมทุกกลุ่มต้องเท่ากับ short รวมทุกกลุ่ม และเท่ากับ open interest ทดสอบทุกครั้งที่ ingest
4. **ทดสอบ revision** — จำลอง CFTC แก้ตัวเลขย้อนหลัง ตรวจว่า `rebuild_derived()` ทำให้สัญญาณอัปเดตตาม

ข้อ 2 สำคัญที่สุด ระบบกฎที่อ่านดูสมเหตุสมผลอาจไม่มีอำนาจทำนายเลย และวิธีเดียวที่จะรู้คือวัดจากข้อมูลจริง แนะนำให้ตั้ง threshold ในตาราง `signal_rule` แล้วจูนจากผล backtest มากกว่าจะยึดค่าเริ่มต้นที่ผมตั้งไว้

## 8. การนำขึ้นระบบ

| ส่วน | ข้อเสนอ |
|---|---|
| Container | 3 service: `api` (uvicorn), `worker` (scheduler), `mysql:8.0` ผูกด้วย docker-compose |
| ความลับ | เก็บใน env ไม่ hardcode `DATABASE_URL`, `ADMIN_API_KEY` |
| การสำรอง | mysqldump รายวันของ `cot_raw` + `price_daily` ส่วนตารางอื่นสร้างใหม่ได้จากสองตารางนี้ |
| Index สำคัญ | ทุก query หลักกรองด้วย `(contract_id, report_date)` ซึ่งเป็น unique key อยู่แล้ว |
| ขยายต่อ | เพิ่มแถวใน `contract` แล้วระบบทั้งหมดรองรับ Silver/Copper/Platinum ได้โดยไม่ต้องแก้โค้ด |
